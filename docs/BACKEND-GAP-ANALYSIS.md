# Buildix — Frontend Design ↔ Backend Gap Analysis

**Sana:** 2026-07-20 · **Ko'lam:** `docs/WebDesign/*.dc.html` (12 ekran) ↔ `Buildix.API` / `Buildix.Application` / `Buildix.Domain` (.NET 9 backend).

Bu hujjat har bir web-dizayn ekranidagi konkret UI imkoniyatini (ko'rsatiladigan data + har bir tugma/filtr/maydon/toggle/ustun/action) mavjud backend bilan solishtiradi. Har bir qator uchun holat:

- ✅ **Supported** — endpoint + DTO maydonlari mavjud.
- ⚠️ **Partial** — endpoint bor, lekin maydon/filtr/param/sub-action yetishmaydi (yoki faqat klient tomonda hal qilinadi).
- ❌ **Missing** — endpoint yo'q / entity maydoni yo'q / imkoniyat umuman yo'q.

> Metod eslatmasi: tahlil `*.dc.html` mockuplarga tayanadi (ular UI niyatini aniq — tugma matni, maydon nomi, toggle yorlig'i darajasida — kodlaydi). `WebDesignPNG/*.png` ayni shu markupning renderlari; ko'plari bayt-bayt bir xil (Account.png = Debts.png = Employees.png = Login.png = Owner Dashboard.png), shu bois `.dc.html` manba sifatida ishlatilgan. Har bir "Missing" xulosasi grep bilan tasdiqlangan (Telegram, SKU/Article, MarketSettings, sessions/login-history — hech biri kodda topilmadi).

## 1. Executive Summary

### Umumiy hisob (taxminiy, ekran bo'yicha noyob imkoniyatlar)

| Holat        | Soni | Izoh                                                                                                                                                                                                 |
| ------------ | ---: | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ✅ Supported |  ~72 | POS/savdo oqimi, mahsulot CRUD, hisobotlar, RBAC, obuna/login — kuchli qamrab olingan.                                                                                                               |
| ⚠️ Partial   |  ~34 | Ko'p ro'yxat ekranlarida server-side search/filter param yo'q; delta/foizlar oldindan hisoblanmagan; ba'zi maydonlar DTO'da ochilmagan.                                                              |
| ❌ Missing   |  ~40 | **Settings (butun MarketSettings modeli), Kassa-smena rekonsiliatsiyasi, naqd yechish tasdig'i (approval), sessiyalar/kirish tarixi, Telegram bildirishnomalar, reorder/PO intellekti** — yiriklari. |

### Eng muhim 8 ta gap (biznes ta'siri bo'yicha)

1. **Settings ekrani deyarli to'liq backendsiz** — `Market` entity'da faqat `Name`/`Description`/`Subdomain`/`ExpiresAt` bor. Do'kon telefoni/manzili/ish soatlari va **barcha** biznes-toggle'lar (only-shift-sale, withdrawal-approval, block-below-cost, default markup %, debt-limit, allowed-discrepancy, auto-close, receipt header/footer, Telegram bildirishnomalar) uchun na entity, na DTO, na update endpoint mavjud. → yangi `MarketSettings` modeli kerak.
2. **Смены (Shifts) ekrani boshqa modelni talab qiladi** — backend `Shift` bu shunchaki ish-vaqti taymeri (`OpenedAt`/`ClosedAt`/`DurationMinutes`). Dizayn esa **kassa-smenasi**: boshlang'ich naqd, smenadagi naqd/karta kirimi, yechimlar, kutilgan qoldiq, **faktik summa va расхождение (discrepancy)**, kassir bo'yicha история смен. Bularning hech biri yo'q.
3. **Naqd yechish tasdiq (approval) oqimi yo'q** — dizayn: "Снятие наличных — с одобрения владельца · Администратор отправляет запрос, вы подтверждаете". Backend'da `POST /api/CashRegister/withdraw` — darhol yechadi; so'rov→tasdiq holati, approve endpoint, request entity yo'q.
4. **Account: sessiyalar, "boshqa sessiyalarni yopish" va kirish tarixi yo'q** — `RefreshToken`'da `DeviceInfo`/`IP`/`LastActiveAt` yo'q; `LoginAttempt` faqat lockout hisoblagichi (per-attempt tarix emas). `AuthController`'da `Login`/`Refresh`/`Logout`dan boshqa hech narsa yo'q.
5. **Telegram integratsiyasi umuman yo'q** — `User`/`Market`'da `Telegram` maydoni yo'q; Settings'dagi 3 ta bildirishnoma toggle'i va "Telegram владельца" hech nimaga ulanmagan (grep: 0 natija).
6. **Zakup: "В пути" (in-transit) statusi va "Рекомендуем заказать" (reorder) + "Создать заказ из списка" (PO) yo'q** — `ZakupReceipt` faqat priyomka (tovar allaqachon keldi); yetkazib-berish holati va sotuv-tezligiga asoslangan reorder tavsiyasi/buyurtma yo'q.
7. **Mahsulot: АРТИКУЛ (SKU/Article) maydoni yo'q; Sotuv/Zakup: sequential «ЧЕК №»/«№» raqami yo'q** — `Product`'da SKU yo'q; `Sale`/`ZakupReceipt` `Id` — Guid, dizayndagi "№1046"/"№214" kabi ketma-ket raqam yo'q.
8. **Ro'yxat ekranlarida server-side qidiruv/filtr param'lari yetishmaydi** — Sales (по чеку/товару/клиенту + оплата + продавец), Warehouse (по названию/артикулу + категория), Debts (по клиенту/телефону + просроченные/сегодня/предстоящие), Employees (по имени/логину + роль), Purchases (по поставщику/накладной). Ko'pi klient tomonda hal bo'ladi, ammo hajm oshgach muammo.

### Qo'shimcha muhim gaplar

- **Debts export yo'q** va Debt DTO'da telefon/customer-type (Юр./Физ. лицо) yo'q; "Платежи сегодня"/"Погашено в этом месяце"/"Просрочено (summa)" stat endpointlari yo'q.
- **Customer'da debt-limit va "постоянный клиент" flag'i yo'q** (Settings'dagi "долг только постоянным" va "лимит долга" qoidalarini backend qo'llay olmaydi).
- **Foydalanuvchi online/last-seen holati yo'q** (Employees "Сейчас в системе"/"4 активных сегодня"); `UserDto`'da telefon ochilmagan.
- **"Забыли пароль?"** — self-service parol tiklash endpoint'i yo'q (dizaynda link `#`).
- **UnitType** faqat Piece/Kilogram/Meter — dizayndagi меш./т/лист./вед. birliklari modellanmagan.
- **Инвентаризация (stocktake)** — bulk hisob/variance oqimi yo'q (faqat Owner bitta mahsulot `Quantity`'sini qo'lda tuzatadi).
